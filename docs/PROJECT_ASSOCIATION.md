# 项目绑定与身份冲突

MacLauncher 只管理用户显式关联的项目。关联有两条路径：**运行时发现**
（应用经 SDK 主动连接并自报身份，用户在管理窗口一次性批准）是免配置的
主路径；**配置文件**（选择项目目录中的 `maclauncher.json`）是可选增强，
提供稳定的服务清单、完整拉起命令与配置刷新。启动器本机保存绑定记录，
绝不自动扫描或猜测项目。

## 运行时发现与批准

1. 应用经 SDK 连接启动器，握手自报项目名、服务声明与可选入口（entry，
   允许完整启动命令：args、工作目录）。
2. 未关联且未被忽略的项目进入**待批准**列表（内存态，按首次发现排序），
   握手以 `pending-approval` 拒绝；应用按重连间隔自动重试属正常。
3. 管理窗口顶部显示待批准卡片：项目名、项目标识、服务清单、来源进程路径、
   首次发现时间；菜单栏同时出现最小提示行「有待批准的应用（N）」。
4. 「批准…」对话框核对身份与来源后建立**运行时绑定**；「忽略」把项目标识
   记入忽略列表（持久化），此后连接静默拒绝，设置页可随时恢复待批准。

运行时绑定的行为差异：

- 无配置文件：界面隐藏「刷新配置」；服务声明由每次握手自报驱动更新
  （新增/删除服务沿用 retained 语义——被删除的声明保留只读记录并清除其
  登录启动偏好）。
- 入口学习：拉起入口来自应用自报（app 包或可执行文件，含完整启动命令）。
  入口路径失效时，断连的卡片显示「入口失效」与修复引导；应用重新运行并
  连接后自报自动自愈。应用未自报入口时仍可批准——仅观察与回收，启动器
  不能拉起该应用。
- 待批准按项目标识记录：解除运行时绑定后，应用重连会重新出现在待批准
  （除非已被忽略）。

## 配置文件格式（schemaVersion 1）

```json
{
  "schemaVersion": 1,
  "project": { "id": "demo-project", "name": "示例项目" },
  "services": [
    { "id": "demo", "name": "演示服务" }
  ],
  "entry": {
    "kind": "executable",
    "path": "build/minimal_app",
    "args": ["demo-project"],
    "workingDirectory": "."
  }
}
```

- `project.id` 是项目身份，必须全局唯一且稳定；改名（`project.name`）不产生新身份。
- `services` 声明管理范围；应用运行时可以声明额外服务，但请求只路由到绑定范围内
  的服务，未知额外服务一律忽略。
- `entry` 为可选拉起入口：`app`（.app 包，经系统 `open` 打开）或
  `executable`（可执行程序，detached 启动，不经 shell）。相对路径与相对
  `workingDirectory` 均以配置所在目录为基准。未配置入口时启动器不接管拉起，
  应用可自行运行并连接。
- 未识别字段被忽略；未知 `schemaVersion` 拒绝关联（`unknown-version`）。

## 配置文件关联

1. 管理窗口点击「关联项目」，选择项目目录中的 `maclauncher.json`。
2. 校验通过且身份、路径均未占用 → 建立绑定；同配置重复关联复用原记录（偏好保留）。
3. 绑定记录保存项目身份、配置文件路径、项目名、服务声明与入口配置（用于拉起与
   路由），本机仅存路径而非配置内容拷贝。

## 身份冲突

冲突只在以下两种情况出现，且绝不自动合并或静默改写：

- **同身份，异路径**：两份配置声明同一个 `project.id`（常见于移动目录或副本）。
  运行时绑定与配置文件撞同一 `project.id` 也归入此类——「迁移原绑定」会把
  该绑定（含登录启动偏好，`boundAt` 保留）转为配置绑定，自报学习的入口随之
  弃用，改以配置文件为准。
- **同路径，异身份**：该路径已绑定到另一个 `project.id`。

弹窗提供两种显式解决方式：

- **迁移原绑定**：要求两份配置身份一致；绑定（含登录启动偏好，`boundAt` 保留）
  移到新路径，原路径不再解析到该绑定。路径被占用或身份不符会被拒绝。
- **作为新项目**：为进入的配置生成新的项目身份（仅改写该文件中的
  `project.id`，其余字段原样保留），形成与既有绑定完全独立的记录。

取消则什么都不改变。

## 配置刷新与失效

启动时与手动刷新时按绑定记录的路径重新读取配置：

- 新增/删除服务、改名按差异更新；被删除声明的服务保留只读记录，其登录启动偏好
  被清除。
- 配置失效（缺失、不可读、版本未知、结构非法）：绑定保留，界面显示具体原因，
  暂停新的拉起与通知；修复后再次刷新自动恢复，不隐式回收或重启业务。
- 失效态引导：失效的项目卡明确给出两条出路——「重新选择配置…」进入修复导向
  流程（找回配置措辞，迁移原绑定后自动恢复；与关联冲突的「项目身份冲突」措辞
  区分），或「解除绑定…」放弃（走「解除绑定」一节的 UnbindFlow 与确认对话框；
  清除启动器侧绑定、偏好与失效/retained 残留，应用运行实例不受影响）。
  引导动作本身（重新选择、一次性说明）不清除 retained 只读记录；清除只发生在
  解除绑定或 retained 行「清除」的逐条路径。解除绑定链路未接线时入口置灰并注明
  「解除绑定将在后续版本提供」。
- 首次进入失效态时弹出一次性说明（什么算失效、数据不会丢、可选出路），经
  PreferenceStore 的 seen 标志（`@guidance.invalidConfigSeen`，缺省视为未读）
  保证不反复弹出。
- 配置声明了不同的 `project.id`：视为身份漂移，绝不自动改写，走上面的冲突流程。

## 解除绑定

解除绑定是显式销毁绑定关系的完整链路，**保留运行**——绝不回收、重启或
改写项目自己的业务与日志：

1. 确认对话框只有一个动作：「保留运行并解除绑定」，同时显示影响摘要
   （将清除的登录启动偏好条数）；取消则一切不变。
2. 入口归还：对已接管的统一入口尽力发送 `setEntryManaged(false)`，短超时
   失败不阻塞解绑（原入口轮询兜底恢复，见 docs/ENTRY_HANDOFF.md）。
3. 关闭该项目的业务连接；界面上的状态监听随卡片移除自动停止。
4. 清除该项目的登录启动偏好、配置失效原因与 retained 记录（含落盘），
   最后删除绑定记录。
5. 解除后该项目按未知身份处理：它再以原身份发起握手会重新进入待批准
   （运行时发现路径），用户可再次批准、加入忽略列表，或置之不理；业务仍
   独立运行。若应用未重启且原生菜单栏进程持有旧身份与路由地址，按未知
   项目处理时需先重启——该流程暂不支持（沿用既有未知项目口径）。

被删除声明的服务在配置刷新后保留只读记录（retained），卡片上提供「清除」
按钮逐条移除，确认后不再复活。
